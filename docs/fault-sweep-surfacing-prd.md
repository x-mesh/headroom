## 1. 한 줄 정의

이 제품에서 가장 강한 출력은 장애 스윕 결과인데 사이드바의 두 번째 탭에 있다. **만들 것 없이 자리만 옮긴다.** 기능 PRD가 아니라 정보 구조 PRD다.

## 2. 범위와 다른 문서와의 경계

`docs/display-layer-improvement-prd.md`와 범위가 겹친다. 소유권을 먼저 정한다.

| 결정 | 소유 문서 |
|---|---|
| 상단 정보 서열. 편집 툴바와 요약의 순서 | `display-layer-improvement-prd.md` 6.3절 |
| 요약 타일의 개수와 구성 | `display-layer-improvement-prd.md` 6.4절 |
| 여유 배수 타일의 내용 | `docs/survival-multiplier-prd.md` 7.1절이 제안, 6.4절이 확정 |
| 스윕 결과가 화면의 어디에 사는가 | **이 문서** |
| 첫 진입에서 무엇을 먼저 보이는가 | **이 문서** |
| 목록의 정렬, 접기, 규모 확장 | **이 문서** |
| 스윕 결과의 접근성 순서 | **이 문서** |
| 스윕의 계산 범위(자원, 도메인, N-2) | `docs/domain-sweep-prd.md` |

이 문서는 6.3절과 6.4절의 요구를 다시 쓰지 않는다. 타일에 관한 내용은 제안으로만 적고 확정을 6.4절에 넘긴다.

## 3. 배경

자원 20개(장비 10, 링크 10) 전부에 N-1 결과가 평문 문장으로 미리 계산되어 붙어 있다.

```
LEAF A   FABRIC / RACK 04   끄면 서비스 단절        UP
EDGE A   EDGE               끄면 82%만 전달         UP
SPINE A → LEAF B  10 Gbps   끄면 견딤 · 한계 미확인  UP
API 01   FABRIC / RACK 04   출발지·목적지 · 끄면 끊김  UP
```

클릭하기 전에 답이 다 있다. draw.io, Lucidchart, Miro, 다이어그램 as 코드 도구 중 어느 것도 이것을 하지 못한다. 그림 도구는 상자를 둘 그리면 이중화처럼 보이게 할 뿐이다.

그런데 이 목록이 `설계 도구` 사이드바의 두 번째 탭(`장애 주입`)에 있고 기본 선택은 `컴포넌트`다. 처음 들어온 사람은 열어보지 않을 가능성이 높다. 제품의 차별점이 한 번의 클릭 뒤에 숨어 있다.

동시에 `단일 장애점 4개`라는 사실이 요약 타일에 없다. 캔버스 푸터 서술에 `단일 장애점이 4개 있습니다. LEAF A 하나만 죽어도 트래픽이 끊깁니다`가 들어 있고 노드에 `SPOF` 배지가 붙지만, 화면 상단의 네 타일(최소 headroom, 과부하 자원, 전달 실패, 활성 장애)에는 없다.

## 4. 목표와 비목표

### 목표

- 첫 화면에서 아무 조작 없이 이 설계의 단일 장애점 개수를 알 수 있다.
- 스윕 결과 목록에 도달하는 비용을 한 번의 클릭에서 0으로 줄인다.
- 자원이 수백 개로 늘어도 목록이 읽히고, 그 과정에서 어떤 단절도 숨지 않는다.
- 스크린리더 사용자가 자원 이름 다음에 바로 판정을 듣는다.

### 비목표

- 스윕 계산 로직. `docs/domain-sweep-prd.md`가 소유한다.
- 요약 타일 개수의 확정. 6.4절이 소유한다.
- 새 패널이나 새 화면 추가. 이 문서는 기존 구성 요소의 자리와 기본값을 바꾼다.

## 5. 현재 정보 구조의 진단

위에서 아래로 본 순서다.

1. 헤더. 상태 칩 하나, 메뉴 셋
2. 시나리오 제어. 배율 슬라이더, 기호 범례
3. **설계 편집 툴바.** 7개 버튼이 최초 로드에서 전부 비활성
4. 요약 타일 4개
5. 3열 본문. `설계 도구` 사이드바, `LIVE TOPOLOGY` 캔버스, `장비 검사` 인스펙터
6. 하단 `설계 변화`

두 가지가 어긋나 있다.

**편집이 판정보다 위에 있다.** 정렬과 가로 분배 버튼이 최소 headroom보다 위에 있고, 첫 화면에서 가장 넓은 줄이 회색 비활성 버튼이다. 이것은 draw.io의 정보 구조이고 이 제품은 그림 도구가 아니다. 이 항목의 결정은 6.3절이 소유하므로 여기서는 진단만 기록한다.

**판정의 가장 강한 부분이 기본 화면에 없다.** 사이드바 기본 탭이 `컴포넌트`이므로 스윕 목록이 보이지 않는다. `컴포넌트` 탭은 장비를 배치하는 도구 모음이고, 이미 완성된 설계를 열었을 때 먼저 필요한 것이 아니다.

## 6. 선택지 비교와 권고

### 6.1 선택지

**A. 사이드바 기본 탭을 `장애 주입`으로 바꾼다.**

얻는 것: 비용 0으로 스윕 목록이 보인다. 코드 변경이 가장 작다.
대가: 설계를 만드는 사람에게 컴포넌트 배치가 한 단계 멀어진다. 빈 설계로 시작했을 때는 끌 장비가 없어서 목록이 비어 있고, 그 화면이 첫인상이 된다.

**B. 요약 타일에 생존성을 올린다.**

얻는 것: 조작 없이 상단에서 SPOF 개수를 본다. 스캔 경로의 가장 윗단이다.
대가: 타일 경쟁. 현재 4개이고 6.4절이 여유 배수 타일을 추가하려 한다. 무엇을 빼거나 합쳐야 한다.

**C. 캔버스 오버레이로 강조한다.**

얻는 것: 위상과 판정이 한자리에서 보인다.
대가: 캔버스 밀도가 올라간다. 노드에 이미 `SPOF` 배지가 있어 중복에 가깝다. 개수를 세는 일은 여전히 사람이 한다.

**D. 하단에 별도 패널을 만든다.**

얻는 것: 목록에 넓은 공간을 준다.
대가: 수직 공간을 먹고 `설계 변화` 패널과 경쟁한다. 사이드바에 이미 있는 것을 두 곳에 두게 된다.

### 6.2 권고

**A의 조건부 버전과 B를 함께 채택한다.** C는 배지로 이미 부분 충족되므로 하지 않는다. D는 중복이므로 하지 않는다.

**조건부 기본 탭.** 진입 시 활성 자원 수가 0이면 `컴포넌트`, 1 이상이면 `장애 주입`을 기본 선택한다. 규칙이 단순하고 결과가 예측 가능하다. 빈 설계로 시작하면 배치 도구가 먼저 오고, 프리셋이나 프로젝트를 열면 판정이 먼저 온다. 사용자가 탭을 직접 바꾼 뒤에는 그 선택을 세션 동안 기억한다.

**타일 재정의 제안.** 타일을 늘리지 않고 `활성 장애` 타일을 상태에 따라 두 가지를 말하는 `생존성` 타일로 바꾼다.

| 상태 | 타일 내용 |
|---|---|
| 장애 주입 없음 | `단일 장애점 4개 · LEAF A 외 3개` |
| 장애 주입 중 | `활성 장애 1 · headroom -85%` |

평상시에 `활성 장애 0`은 정보가 없는 칸이다. 그 자리가 비어 있는 동안 SPOF 개수를 말하게 하면 타일 개수가 늘지 않는다. 확정은 6.4절이 한다.

## 7. 기능 요구사항

### 7.1 조건부 기본 탭

진입 시 활성 자원 수에 따라 사이드바 기본 탭을 정한다. 사용자가 탭을 바꾸면 세션 동안 그 선택을 유지한다.

**인수 기준.** 기본 시나리오로 진입하면 `장애 주입` 탭이 선택된 상태다. 빈 설계로 시작하면 `컴포넌트` 탭이 선택된다. 탭을 수동으로 바꾼 뒤 재계산이 일어나도 선택이 유지된다.

### 7.2 생존성 타일

6.6절의 제안대로 타일이 상태에 따라 다른 것을 말한다. 타일을 클릭하면 `장애 주입` 탭이 열리고 해당 목록으로 초점이 이동한다.

**인수 기준.** 장애 주입이 없는 상태에서 타일에 단일 장애점 개수가 보이고, 클릭하면 `장애 주입` 탭이 열린다.

### 7.3 정렬

목록을 심각도 우선으로 정렬한다. `severs` → `overloads` → `absorbs`, 동급은 전달률 낮은 순, 그다음 자원 id 사전순이다. DOM 순서가 정렬 순서와 같아야 한다. 키보드 순회가 심각한 항목부터 닿게 하려는 것이다.

현재 목록은 장비와 링크를 나눈 다음 입력 순서로 보이는 것으로 **추정한다. 확인 필요.**

**인수 기준.** 기본 시나리오에서 `끄면 서비스 단절` 항목이 목록 맨 위에 온다.

### 7.4 접기와 숨김의 구별

`severs`와 `overloads` 항목은 항상 펼쳐져 있다. `absorbs` 항목은 접을 수 있고, 접힌 상태에서도 **개수가 항상 보이고 한 번의 조작으로 펼쳐진다.**

상위 PRD의 원칙상 있는 단일 장애점을 안 보이게 만드는 설계는 허용되지 않는다. `absorbs`는 "문제 없음"이라 접어도 정보가 사라지지 않지만, 개수가 사라지면 숨김이 된다.

**인수 기준.** `absorbs` 묶음을 접은 상태에서 개수가 화면에 보이고, `severs` 항목은 어떤 상태에서도 접히지 않는다.

### 7.5 유도 경로

캔버스 푸터의 `FW A 장애 실험` 패턴을 유지하고 선정 규칙을 정한다. 우선순위는 다음과 같다.

1. 이중화 무효로 판정된 도메인이 있으면 그 도메인 실험(`docs/domain-sweep-prd.md` 4.5절)
2. 없고 `severs` 자원이 있으면 그 자원
3. 없으면 병목 축이 대역폭이 아닌 자원. 현재 기본 시나리오가 이 경로로 `FW A`를 고르고 있고 교육 효과가 가장 크다

**인수 기준.** 도메인이 정의되고 이중화 무효 판정이 나오면 유도 버튼이 그 도메인 실험으로 바뀐다.

### 7.6 내보내기

설계 리뷰에 첨부하는 산출물에 "이 설계의 단일 장애점은 이것들이다"가 실려야 한다. 현재 결과 JSON과 SVG/PNG에 스윕 결과가 어느 범위까지 들어가는지 **확인 필요**이고, 다음을 요구사항으로 둔다.

- 결과 JSON: 자원별 등급과 판정 문장, 단일 장애점 목록, 등급 집계
- SVG / PNG: 단일 장애점 개수와 목록 요약. 노드의 `SPOF` 배지는 이미지에도 나타난다

**인수 기준.** 결과 JSON에 단일 장애점 자원 id 목록이 있고, SVG에 단일 장애점 개수가 텍스트로 들어 있다.

## 8. 규모 확장

비기능 목표가 노드 200 / 링크 500이므로 자원 700개 시나리오가 범위 안이다. 도메인 스윕이 들어오면 항목이 더 늘어난다.

- **가상 스크롤.** 목록을 가상화한다. 접근성과 충돌하지 않게 `aria-setsize`와 `aria-posinset`을 제공한다.
- **묶기.** `zone` 또는 장애 도메인 단위로 묶어 접을 수 있게 한다. 묶음 헤더에 그 묶음의 최악 등급과 개수를 적는다.
- **필터.** 등급 필터와 이름 검색. 필터가 걸린 동안 `필터 적용 중 · 전체 700 중 12개 표시`를 상시로 보인다. 필터 상태가 보이지 않으면 숨김과 구별되지 않는다.
- **금지.** 상위 N개만 계산하거나 표시하고 나머지를 버리지 않는다. 전수를 계산했다면 전수에 도달할 경로가 있어야 한다.

`severs`가 수십 개인 설계도 있을 수 있다. 그때도 전부 도달 가능해야 하고, 묶기와 가상 스크롤로 해결한다. 잘라내기로 해결하지 않는다.

**인수 기준.** 자원 700개 시나리오에서 목록 스크롤이 끊기지 않고, `severs` 항목 전부에 키보드로 도달할 수 있다.

## 9. 접근성

### 9.1 읽는 순서

목록 항목의 접근 가능한 이름은 자원명 다음에 **판정이 오고** 그다음 현재 상태가 온다. 탐색 중에 이름만 듣고 넘어가면 목록의 가치가 사라진다.

```
LEAF A, 끄면 서비스 단절, FABRIC / RACK 04, 현재 UP
```

현재 구현은 `LEAF A FABRIC / RACK 04 끄면 서비스 단절 UP` 순서로 **추정**되며 영역이 판정보다 앞에 있다. 순서를 바꾼다.

### 9.2 색상에 의존하지 않는다

상위 PRD 10절이 상태를 색상만으로 구분하지 않기로 했다. 등급 표시에 기존 기호 체계를 쓴다. `display-layer-improvement-prd.md` 7.3절이 기호를 형태로 바꾸기로 했으므로 같은 기호를 쓴다.

### 9.3 구조와 상태

- 섹션 제목을 유지한다. 현재 `장비`, `링크`, `장애 도메인`이 heading으로 있다.
- 목록을 `list` / `listitem`으로 표시하고 가상 스크롤 시 `aria-setsize`, `aria-posinset`을 채운다.
- 접기 컨트롤에 `aria-expanded`를 둔다.
- 장애를 주입하면 요약 변화를 라이브 영역으로 알린다. 페이지에 `status` 역할 요소가 존재하는 것을 확인했으나 현재 용도는 **확인 필요**다. 재사용할 수 있으면 재사용한다.

**인수 기준.** 키보드만으로 목록을 순회해 가장 심각한 항목에 먼저 닿고, 각 항목에서 판정을 자원명 직후에 듣는다. 장애를 주입하면 최소 headroom 변화가 라이브 영역으로 통지된다.

## 10. 검증 전략

**기본 탭 규칙.** 활성 자원 0개와 1개 이상 각각에서 기본 탭이 규칙대로 선택된다. 수동 선택 후 재계산에서 선택이 유지된다.

**정렬.** 무작위 순서로 구성한 토폴로지에서 DOM 순서가 심각도 순서와 일치한다. 동점 처리가 결정적이다.

**숨김 금지.** `absorbs`를 접은 상태에서 개수 텍스트가 DOM에 있다. `severs` 항목에 접기 컨트롤이 없다.

**필터 가시성.** 필터가 걸린 동안 전체 개수와 표시 개수가 DOM에 있다.

**전수 도달.** 자원 700개에서 모든 `severs` 항목이 키보드 순회로 도달 가능하다.

**접근 가능한 이름 순서.** 모든 목록 항목의 접근 가능한 이름에서 판정 문구가 영역 문구보다 앞에 온다.

**라이브 통지.** 장애 주입 후 라이브 영역의 텍스트가 변경된다.

**내보내기.** 결과 JSON에 단일 장애점 목록이 있고 SVG에 개수가 있다.

## 11. 결정 사항과 미결 사항

### 결정됨 (v0.1)

**조건부 기본 탭을 쓴다.** 활성 자원 0개면 `컴포넌트`, 1개 이상이면 `장애 주입`. 수동 선택은 세션 동안 유지한다.

**타일을 늘리지 않고 `활성 장애`를 재정의한다.** 제안이며 확정은 6.4절이 한다.

**심각도 우선 정렬이고 DOM 순서가 정렬 순서와 같다.**

**`severs`와 `overloads`는 접히지 않는다.** `absorbs`만 접히고 개수는 항상 보인다.

**잘라내기로 규모를 해결하지 않는다.** 가상 스크롤과 묶기로 해결한다.

**접근 가능한 이름에서 판정이 영역보다 앞에 온다.**

### 미결

**현재 정렬 규칙.** 목록이 지금 어떤 순서인지 소스에서 확인 필요.

**내보내기에 들어가는 스윕 범위.** 결과 JSON과 이미지에 현재 무엇이 실리는지 확인 필요.

**`status` 역할 요소의 현재 용도.** 라이브 통지에 재사용할 수 있는지 확인 필요.

**도메인 결과의 자리.** 같은 탭의 `장애 도메인` 절에 둘지 자원 목록과 섞어 심각도로 정렬할지. 섞으면 심각도 순서가 일관되지만 자원과 도메인의 성격 차이가 흐려진다. `docs/domain-sweep-prd.md`와 함께 정한다.

**묶기의 기본값.** 자원 수가 얼마를 넘으면 자동으로 묶을지.

**탭 이름.** `장애 주입`은 행위를 말하고 목록의 내용은 판정이다. `생존성 검사` 같은 이름이 더 맞을 가능성이 있다. 다만 이름을 바꾸면 기존 사용자의 기억과 어긋난다.

## 12. 작업 순서

1. 정렬. 현재 규칙을 확인하고 심각도 우선으로 바꾼다. 가장 싸고 효과가 크다.
2. 접근 가능한 이름 순서 교정.
3. 조건부 기본 탭.
4. 생존성 타일. 6.4절 작업과 함께 진행한다.
5. 유도 경로 선정 규칙. 도메인 판정이 생긴 뒤에 1순위가 의미를 갖는다.
6. 내보내기 확인과 보강.
7. 규모 확장. 가상 스크롤, 묶기, 필터. 700개 시나리오를 만들어 측정한 뒤 착수한다.

## 13. 손대지 말 것

- 결과 문장의 문구. `끄면 서비스 단절`, `끄면 82%만 전달`, `끄면 견딤 · 한계 미확인`은 평문이고 잘 작동한다. 내부 용어로 바꾸지 않는다.
- 클릭하면 해당 자원이 `DOWN`이 되고 전체가 재계산되는 동작.
- 캔버스 푸터의 서술 문구와 유도 버튼 패턴. 선정 규칙만 바꾼다.
- 노드의 `SPOF` 배지. `docs/domain-sweep-prd.md` 6.3절이 확장을 소유한다.
