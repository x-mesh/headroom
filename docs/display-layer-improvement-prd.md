# Rack Mesh — 표시 계층 개선 PRD

작성일: 2026-09-09
개정: v0.1 (초안)
상위 문서: `infra-simulator-prd.md` v0.5
상태: 초안 (Draft)
작성 배경: engine 3.0.0 빌드(`Dual fabric API cluster` 시나리오)를 실행 상태에서 검토한 결과

---

## 1. 한 줄 정의

계산은 이미 맞다. 이 문서는 **계산 결과를 화면이 어떻게 말하는가**를 고친다. 표시 계층이 원본 PRD의 원칙 세 개를 어기고 있고, 제품을 다른 도구와 갈라놓는 기능들이 기본 시나리오에서 보이지 않는다.

## 2. 배경

engine 3.0.0 빌드는 원본 PRD가 약속한 것 대부분을 이미 구현했다. 축별 다차원 사용률, 병목 축 지목, 미확인 축의 통과 판정 보류, 기준선 비교, 20개 자원 전체의 N-1 사전 계산이 모두 동작한다. `검증 설정`에는 서비스 생존성, 장애 도메인, 랙 예산이 이미 들어와 있고, `engine.js`는 축마다 `source.type`과 `evidenceApplicability`를 붙인다.

문제는 다른 층에 있다.

첫째, **화면이 사실이 아닌 것을 말한다.** 과부하 상태에서 요약 타일은 `전달 실패 0 · 0 Mbps 미전달`인데 같은 화면의 서술은 `2.2 Gbps가 버려집니다`라고 적는다. 헤더 상태 칩은 `EVIDENCE INCOMPLETE`를 `CAPACITY EXCEEDED`로 덮어 미확인 축이 남아 있다는 사실을 지운다. 떨림이 켜진 상태에서 `7.10G`가 `74%`로 찍혀 한 라벨 안에서 산술이 깨진다.

둘째, **차별점이 첫 화면에서 보이지 않는다.** 기본 시나리오의 서비스, 장애 도메인, 랙, 시나리오가 모두 0개다. 캔버스에는 이미 `SPOF` 배지와 `RACK 04` / `RACK 07` 영역이 그려져 있는데 그 뒤에 아무 정의도 없다. "이 이중화는 실은 이중화가 아니다"를 말할 골격만 있고 내용이 없다.

셋째, **움직임 예산을 반대로 쓰고 있다.** 아무 일도 없을 때 숫자가 떨리고, 실제로 값이 바뀌는 순간의 260ms 트윈은 그 소음에 묻힌다. 패킷 점 속도는 사용률에 연동되어 있지만 `animateMotion`의 `dur`가 경로 길이와 무관해서 결과적으로 그림의 길이를 말한다.

## 3. 목표

- 화면에 표시되는 모든 수치가 엔진 결과와 산술적으로 일치한다.
- 손실, 미확인, 과부하 중 어느 것도 다른 것에 가려지지 않는다.
- 움직임이 장식이 아니라 정보를 운반한다. 무엇이 확정되지 않았는지, 어디서 트래픽이 막히는지를 말한다.
- 기본 시나리오만으로 제품의 차별점 세 가지(다축 한계, 공유 장애 도메인, 서비스 수용 기준)가 전달된다.

### 비목표

- 계산 엔진 변경. 이 문서의 모든 항목은 표시 계층, 마크업, 기본 시나리오 데이터에서 해결된다.
- 새 다이어그램 편집 기능. 원본 PRD 12절이 정한 대로 이 도구는 그림 도구가 아니다.
- 확률적 가용성 산출. 생존성은 결정적으로 계산하고 확률은 도입하지 않는다.
- 외부 요청. 실측 임포트는 파일 기반으로만 한다(10절 개인정보 항목 유지).

## 4. 새 원칙: 표시 효과는 데이터 출처가 정한다

원본 PRD 7.2가 정의한 `source.type`을 표시 계층의 지배 조건으로 승격한다.

떨림은 장식이 아니라 **"이 값은 아직 확정되지 않았다"**는 뜻이다. 확정된 값은 움직이지 않는다. 이 정의를 받아들이면 떨림이 "모르는 것을 안전으로 바꾸지 않는다"는 원칙과 싸우지 않고 그 원칙을 시각화한다.

| `source.type` | 진폭 | 읽는 법 |
|---|---|---|
| `estimate` | 4% | 가정값. 자리만 잡은 숫자 |
| `datasheet` | 1.5% | 벤더 주장. 이 환경에서 미검증 |
| `third_party_test` | 1% | 독립 시험. 이 환경에서 미검증 |
| `user_measured` | 0% | 이 환경의 실측. 인용 가능 |
| `user-correction` | 0% | 사용자가 단언한 값 |
| 임포트한 실측 부하 | 0% | 사실. 어떤 경우에도 움직이지 않는다 |

부수 효과가 이 원칙의 핵심이다. **근거를 채울수록 화면이 조용해진다.** 정지 자체가 신호가 된다. 설계 초기에는 캔버스가 살아 움직이고, 검증이 끝나면 멈춘다. 별도 진행률 지표 없이 근거 확보 상태가 그림으로 드러난다.

### 4.1 출처와 무관하게 지켜야 할 불변 조건

1. **파생값은 같은 교란에서 나온다.** 백분율과 부하는 하나의 축 단위 파동을 같은 비율로 곱한다. `percent = load / limit`이 언제나 성립한다.
2. **판정은 원값으로 한다.** 상태 분류, 병목 축 선정, SPOF 판정, 통과 보류는 교란되지 않은 값을 읽는다. (현재 빌드에서 이미 성립. 상태 클래스가 렌더 시점에 결정되고 `paintLive()`는 텍스트와 막대 길이만 다시 칠한다.)
3. **집계값은 떨지 않는다.** 최소 headroom, 여유 배수, 기준선 비교, 서술 문구, 요약 타일. (현재 `.binding-callout` 제외와 요약 타일의 `data-live-*` 미사용으로 대부분 성립. 6.4에서 타일을 추가할 때 유지한다.)
4. **내보내기는 원값을 담는다.** (현재 성립. `diagramSvg()`가 `exportDiagramSvg(topology, current, ...)`를 불러 화면 DOM이 아니라 엔진 결과에서 다시 그리고, PNG는 그 SVG를 캔버스로 옮긴다. 떨림 프레임이 파일에 굳지 않는다.)
5. **`prefers-reduced-motion`에서 꺼진다.** (현재 성립.)

### 4.2 선행 조건

- 축별 출처를 마크업으로 실어 나른다. 값은 이미 계산되지만 DOM에 없어서 모션 루프가 볼 수 없다.
- 링크 정격에 `type`이 없다. 포트 속도는 확정값이므로 `datasheet`로 명시한다. 기본값 `estimate`로 흘러들어가 흔들리게 두면 안 된다.
- 실측 한계를 파일로 받는 임포트 형식.

## 5. P0 — 화면이 사실이 아닌 것을 말한다

이 세 항목이 해결되기 전에는 나머지가 의미 없다.

### 5.1 요약 타일이 손실을 0으로 보고한다

**현상.** `FW A` 비활성 상태에서 요약 타일 `전달 실패 0 · 0 Mbps 미전달`, 같은 화면 서술 `병목을 지나지 못한 2.2 Gbps가 버려집니다. 신규 세션 30 Kcps가 거절됩니다`.

**원인.** 무경로(unreachable)와 용량 드롭(bottleneck discard)이 서로 다른 값인데 라벨 하나를 공유하고, 첫 번째만 센다.

**요구사항.** 두 손실을 각각 표시하고 합치지 않는다. `미전달 2.2 Gbps 드롭 · 0 Mbps 무경로` 형태로 한 타일에 두 값을 두거나 타일을 분리한다. 드롭이 0이 아닌데 타일이 0을 보이는 상태가 존재해서는 안 된다.

**인수 기준.** 임의의 장애 주입 조합에서 요약 타일의 손실 합계가 서술 문구의 손실 합계와 일치한다.

### 5.2 백분율과 부하가 독립적으로 교란된다

**현상.** 떨림 켬 상태에서 입력 변화 없이 5회 샘플링한 `FW B`.

```
BPS 7.25G 70%   CPS 72.2K 173%
BPS 7.28G 72%   CPS 70.6K 170%
BPS 7.10G 74%   CPS 71.5K 170%
BPS 7.09G 72%   CPS 72.8K 172%
BPS 7.25G 71%   CPS 71.7K 172%
```

떨림 끔에서는 4회 모두 `BPS 7.20G 72% · CPS 72.0K 171%`로 고정된다. 한계 10 Gbps 기준으로 `7.10G`는 71%여야 하는데 74%로 찍힌다.

**원인.** 같은 축의 두 노드에 다른 시드가 붙는다(`{id}:{axis}` 대 `{id}:{axis}-load`). `telemetryWave()`가 시드를 해시하므로 파동이 갈린다. 게다가 백분율은 퍼센트포인트로 더하고 부하는 비율로 곱한다.

**요구사항.** 축 단위 파동 하나를 두 노드가 같은 비율로 곱한다. 백분율의 덧셈 적용을 폐기한다. 낮은 값이 반올림에 묻히는 문제는 출처별 진폭이 대신 해결한다. `estimate` 축은 20%에서 ±0.8퍼센트포인트로 충분히 보이고, `datasheet` 축이 거의 움직이지 않는 것은 그 숫자가 더 단단하기 때문에 옳다.

**인수 기준.** 떨림 켬 상태에서 모든 축의 표시 백분율과 `표시 부하 / 한계`가 1e-6 이내로 일치한다.

### 5.3 헤더 상태 칩이 두 상태를 한 칸에 담는다

**현상.** 최초 로드 `EVIDENCE INCOMPLETE` → 장애 주입 후 `CAPACITY EXCEEDED`. 미확인 축은 그대로인데(`API 01` / `API 02`의 `NPPS —`) 증거 경고가 사라진다.

**원인.** 증거 완전성과 용량 상태는 직교하는 축인데 단일 슬롯을 우선순위로 나눠 쓴다.

**요구사항.** 두 칩이 공존한다. `EVIDENCE 4 UNKNOWN`과 `CAPACITY EXCEEDED`. 하나가 다른 하나를 덮는 상태를 없앤다.

## 6. P1 — 차별점이 보이지 않는다

### 6.1 기본 시나리오에 검증 객체를 채운다

**현상.** `분석 → 검증 설정`이 `서비스 0`, `장애 도메인 0`, `랙 0`, `시나리오 0`. 장애 주입 패널 하단은 `장애 도메인 — 아직 없습니다`. 캔버스에는 `SPOF` 배지와 `RACK 04` / `RACK 07`이 이미 그려져 있다.

**왜 중요한가.** 기본 시나리오는 지금 "방화벽이 대역폭보다 CPS에 먼저 걸린다"는 교훈 하나를 잘 가르친다. 그런데 공유 장애 도메인 교훈은 전혀 가르치지 못한다. 후자가 더 어렵고 더 값진 교훈이며, draw.io 대비 우위가 가장 선명한 지점이다. draw.io는 상자를 둘 그리면 이중화처럼 보인다.

또한 서비스가 0개면 통과 판정을 평가할 기준 자체가 없다. 판정 도구가 판정 기준 없이 시작한다.

**요구사항.** `Dual fabric API cluster` 시나리오에 다음을 포함한다.

- 장애 도메인 `RACK 04` = { LEAF A, API 01 }, `RACK 07` = { LEAF B, API 02 }. 도메인 하나를 끄면 이중 패브릭 설계가 서비스 절반을 잃는다는 사실이 한 번의 클릭으로 드러난다.
- 서비스 `Public API`, 최소 전달률 99%, `Public API` 수요에 연결. 통과 판정이 평가할 기준이 생긴다.
- 랙 하나에 전력 예산과 U 공간. 대역폭이 아닌 축이 먼저 병목이 되는 사례가 도달 가능해진다.

**인수 기준.** 첫 화면에서 아무 편집도 하지 않고 세 가지 교훈(다축 한계, 공유 장애 도메인, 서비스 수용 기준)에 각각 한 번의 클릭으로 도달할 수 있다.

### 6.2 패킷 점이 무엇을 말하는지 고친다

**현상 정정.** 점 속도는 이미 사용률에 연동되어 있다(`duration = max(1.25, 3.4 - min(share, 1.5) * 1.25)`). 밀도도 1~3개로 변한다. 결함은 연동 방식에 있다.

1. `animateMotion`의 `dur`는 경로 길이와 무관하다. 체감 속도는 `경로길이 / dur`이므로, 26%인 긴 링크가 85%인 짧은 링크보다 빨라 보인다. 속도가 사용률이 아니라 그림의 길이를 말한다.
2. 범위가 좁다. 0%가 3.4초, 150%가 1.53초로 전 구간 2.2배. 85%와 26%의 차이가 2.34초 대 3.08초라 인식되지 않는다.
3. 과부하가 잘려 있고 정직하지 않다. `min(share, 1.5)` 때문에 122%와 171%가 같게 움직이고, **버려지는 트래픽까지 점이 끝까지 도착한다.** 서술이 "2.2 Gbps가 버려집니다"라고 적는 동안 그림은 전부 도착한다고 그린다.

**요구사항.**

- 속도를 px/s로 정규화한다. 렌더 직전에 경로 길이를 재서 `dur`를 계산한다. 사용률이 같으면 링크 길이와 무관하게 같은 속도로 보인다.
- 범위를 넓힌다. 유휴 30 px/s, 100% 115 px/s.
- 과부하는 느려진다. 100%를 넘으면 12 px/s로 떨어져 정체로 읽힌다. 빠른 빨간 링크는 반대 뜻이다.
- 통과 비율만큼만 이동한다. `reach = min(1, 1/share)`. 122% 링크의 점은 82% 지점에서 사라진다. 링크 라벨의 숫자와 같은 사실을 그림이 말한다.

| 사용률 | 점 개수 | 이동 거리 | 체감 속도 |
|---|---|---|---|
| 0.26 | 1 | 전체 | 52 px/s |
| 0.85 | 3 | 전체 | 102 px/s |
| 1.00 | 3 | 전체 | 115 px/s |
| 1.22 | 4 | 82% 지점에서 소멸 | 12 px/s |
| 1.71 | 4 | 58% 지점에서 소멸 | 12 px/s |

**인수 기준.** 길이가 다른 두 링크가 같은 사용률일 때 체감 속도(px/s)가 클램프 구간 밖에서 일치한다. 사용률 1을 넘는 링크의 점이 경로 끝에 도달하지 않는다.

### 6.3 판정이 편집보다 위에 온다

**현상.** 레이아웃 순서가 헤더 → 시나리오 제어 → **설계 편집 툴바** → 시나리오 요약 → 캔버스. 정렬과 분배 버튼이 최소 headroom보다 위에 있고, 최초 로드에서 툴바 7개가 전부 비활성이라 첫 화면에서 가장 넓은 줄이 회색이다.

**요구사항.** 요약을 편집 툴바 위로 올리거나, 편집 컨트롤을 캔버스 크롬 안으로 넣고 정렬·분배는 다중 선택 시에만 드러낸다.

### 6.4 여유 배수를 타일로 승격한다

**현상.** `1.16배에서 초과`가 캔버스 헤더 부제의 작은 글씨로 들어가 있고, 타일은 `최소 headroom 14%`가 차지한다.

**왜 중요한가.** 배수는 배포 이후 역할("현재 스펙으로 얼마나 버티나")의 답 형식이고 암산이 필요 없다. 백분율은 읽는 사람이 배수로 환산해야 한다.

**요구사항.** `여유 배수` 타일을 추가한다. `1.16× 까지 · 다음 병목 leaf-b-api-b BPS`. 최소 headroom은 부차 지표로 유지한다. 4.1의 불변 조건 3에 따라 이 타일은 떨지 않는다.

## 7. P2 — 움직임 예산, 출처 고지, 상태 위생

### 7.1 움직임을 유휴에서 전환으로 옮긴다

**재계산 트윈은 이미 구현되어 있다.** `MOTION.tween = 260ms`에 cubic ease-out, 첫 렌더와 reduced-motion에서 건너뜀. 만들 것이 없다. 다만 지금은 **들리지 않는다.** 유휴 떨림이 위에서 계속 돌아 진짜 260ms 재계산이 주변 소음과 구분되지 않는다. 4절의 출처 게이트가 이 애니메이션을 처음으로 읽히게 만든다.

추가로 두 가지를 넣는다.

- **최초 진입 티저.** 첫 로드에서 워크로드 배율을 1.00 → 1.20 → 1.00으로 약 3초에 걸쳐 한 번 훑는다. 값이 실제로 변하고 병목이 실제로 이동한다. 이 도구가 살아 있는 계산기라는 것을 거짓 없이 증명하고 멈춘다. 위의 트윈 엔진이 그대로 렌더한다.
- **사건 펄스.** 병목 축이 바뀌는 순간 해당 노드가 한 번 번쩍인다. 반복이 아니라 사건이다.

### 7.2 합성값 표시가 내보내기에서 사라진다

**현상.** 노드에 실제 제조사(`Fortinet`, `Juniper Networks`, `Arista`, `Cisco`, `Dell`)와 합성 모델명(`DEMO-FW-42K`)이 함께 찍히는데, `합성 데모 값` 배지는 인스펙터에만 있다. SVG와 PNG로 내보내면 제조사명과 숫자만 남고 그 숫자가 지어낸 값이라는 표시가 사라진다.

**요구사항.** 원본 PRD 8절이 요구하는 출처, 조건, 엔진 버전을 이미지 내보내기에 새겨 넣는다. 캔버스 노드에도 합성값 표시를 단다.

### 7.3 상태 기호가 접근성 부담을 감당하지 못한다

**현상.** 범례 `. 정상 / ! 주의 / > 용량 초과 / ? 한계 미확인 / x 비활성`. 마침표를 정상 표시로 쓰는 것은 노드 크기에서 거의 보이지 않는다.

**요구사항.** 색상만으로 구분하지 않는다는 의도는 유지하고, 구별 가능한 형태(원, 삼각형, 사각형)로 바꾼다.

### 7.4 주입한 장애가 새로고침 후에도 남고 초기화가 묻혀 있다

**현상.** 로컬 저장소에 상태가 남아 새로고침해도 `FW A`가 꺼진 채로 시작한다. 초기화는 `분석 → 장애와 배율 초기화` 두 단계 안이다.

**왜 문제인가.** 운영 보조재로 쓸 때는 유용하지만, 데모와 공유에서는 다음 사람이 남의 실험 상태에서 시작한다.

**요구사항.** 장애나 1.00배가 아닌 배율이 활성인 동안 활성 장애 타일 옆에 `기준 상태로` 컨트롤을 노출한다.

## 8. 검증 전략

원본 PRD 9절에 다음 회귀 테스트를 추가한다.

**결정성.** 떨림 끔 상태에서 같은 토폴로지를 두 번 렌더하면 모든 live 노드의 `textContent`가 바이트 단위로 같다.

**산술 일치.** 떨림 켬 상태에서 모든 축 노드 쌍에 대해 표시 백분율과 `표시 부하 / 한계`가 1e-6 이내로 일치한다. **이 테스트는 현재 빌드에서 실패한다.** 먼저 넣고 고치는 순서로 진행한다.

**판정 무오염.** 임계값에서 2% 이내에 있는 값에 대해 떨림 켬과 끔의 상태 클래스가 동일하다.

**출처 게이트.** `driftAmplitude`가 `user_measured`와 `user-correction`에 0을 반환한다. 모든 축이 `user_measured`인 장비는 떨림 켬과 끔의 출력이 동일하다.

**손실 보존.** 임의의 장애 주입 조합에서 요약 타일의 손실 합계와 서술 문구의 손실 합계가 일치한다.

**패킷 기하 독립성.** 길이가 다른 두 링크가 같은 사용률일 때 `이동거리 / dur`가 클램프 구간 밖에서 일치한다. `packetPixelSpeed`가 `[0, 1]`에서 단조 비감소이고, `share > 1`이 항상 가장 느린 값을 반환한다.

## 9. 결정 사항과 미결 사항

### 결정됨 (v0.1)

**떨림의 의미를 재정의한다.** "살아 있음"이 아니라 "확정되지 않음"이다. 폭은 `source.type`이 정하고, 실측값은 움직이지 않는다.

**엔진은 건드리지 않는다.** 이 문서의 모든 항목은 표시 계층, 마크업, 기본 시나리오 데이터에서 해결한다.

**과부하는 느려진다.** 빠른 빨간 링크가 아니라 정체로 그린다. 통과하지 못하는 몫은 경로 끝에 도달하지 않는다.

**기본 시나리오가 세 교훈을 모두 담는다.** 다축 한계, 공유 장애 도메인, 서비스 수용 기준.

### 미결

**실측 한계 임포트 형식.** 조건과 포화 증거를 어떤 스키마로 받을지. 파일 기반이라는 제약은 확정이지만 형식은 미정이다.

**임포트 데이터의 신선도 표기.** 프로젝트 파일에 `as_of`를 넣기로 하면 화면 어디에 어떤 문구로 표시할지, 얼마나 지나면 경고할지 정해야 한다.

**티저의 옵트아웃.** 최초 진입 티저를 한 번만 보일지, 세션마다 보일지, 끄는 설정을 둘지.

**출처별 진폭 수치.** 4절의 4% / 1.5% / 1%는 첫 제안값이다. 실제 화면에서 `estimate`와 `datasheet`가 구별되는지 확인한 뒤 조정한다.

**링크 정격의 출처 표기.** 포트 속도를 `datasheet`로 두기로 했으나, 사용자가 직접 입력한 링크 정격을 `user-correction`으로 승격할지 결정해야 한다.

## 11. 손대지 말 것

현재 빌드에서 이미 옳게 동작하며 이 문서의 어떤 항목도 이것들을 바꾸지 않는다.

- 미확인 한계가 통과 판정을 보류시킨다. 안전 상태로 기본값을 주지 않는다.
- 장애 주입 목록이 20개 자원 전체의 N-1을 결과 문장으로 미리 계산한다(`끄면 서비스 단절`, `끄면 82%만 전달`, `끄면 견딤 · 한계 미확인`).
- 기준선 비교가 하단에 고정되어 델타뿐 아니라 병목 축 변경을 보고한다.
- 서술 푸터가 상태에 따라 다시 쓰이고 병목 축이 왜 옮겨졌는지 말한다.
- `순서 미확정 2개`가 비결정적 동점 처리를 숨기지 않고 드러낸다.
- 내보내기에 이미지와 함께 JSON이 있어 분석 경로가 이미지 전용이 아니다.
- 미확인 방향에는 패킷 점을 그리지 않는다. 모르는 양을 움직이는 점으로 그리면 사실이 된다.
