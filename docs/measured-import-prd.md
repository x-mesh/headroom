작성일: 2026-09-09

## 1. 한 줄 정의

운영 중인 인프라에서 측정한 값을 파일로 받아, **데이터시트 추정을 이 환경의 사실로 교체한다.** 한계의 실측과 부하의 실측은 성격이 다르므로 따로 받는다.

## 2. 배경

상위 PRD 13절의 최대 미결은 "성능 데이터 수집 방식: 초기 30종을 누가 어떻게 채울지"다. 카탈로그 30종을 채우는 것은 끝이 없는 콘텐츠 작업이고 차별점도 아니다. 경쟁 도구도 같은 데이터시트를 읽는다. 반대로 "내가 실제로 운영하는 장비를 실측으로 채우는 경로"는 같은 방식으로 복제되지 않는다.

그리고 이것이 표시 계층의 전제 조건이다. `docs/display-layer-improvement-prd.md` 4절이 "떨림 폭은 `source.type`이 정한다. 실측값은 움직이지 않는다"를 원칙으로 세웠고, 근거를 채울수록 화면이 조용해지는 설계를 택했다. 그런데 실측을 넣을 경로가 없어서 지금은 모든 값이 `estimate`나 `datasheet`이고 전부 흔들린다. 그 원칙은 이 임포트 없이는 작동하지 않는다.

기반은 이미 있다. `source.type`에 `user_measured`가 정의되어 있고 UI 라벨도 `실측`으로 있다. `evidenceApplicability`가 조건 일치를 판정하고 불일치 시 축을 `unknown`으로 만든다. `acceptanceDigest`로 수락을 봉인한다. 빠진 것은 **값이 들어오는 문**이다.

## 3. 목표와 비목표

### 목표

- 장비 한계의 실측값을 성능층 근거로 등록한다.
- 현재 부하의 관측 스냅샷을 받아 여력 계산의 출발점으로 쓴다.
- 관측값을 한계로 잘못 승격시키지 않는다. 이것이 이 문서의 핵심 제약이다.
- 데이터시트 근거와 관측값이 모순될 때 그 모순을 드러낸다.
- 임포트 데이터가 낡거나 토폴로지와 맞지 않으면 조용히 틀리지 않는다.

### 비목표

- 외부 연결. 모니터링 API를 직접 호출하지 않는다. 상위 PRD 10절의 "기본 실행은 외부 요청을 보내지 않는다"를 유지하므로 파일 임포트만 한다.
- 모니터링 제품별 원본 포맷 해석. 제품이 특정 수집기의 내보내기 스키마를 추측하지 않는다. 7절에서 이유와 대안을 적는다.
- 시계열 보관. 한 시점의 스냅샷을 받고 추세를 저장하지 않는다. 성장률 예측은 범위 밖이다.
- 실시간 갱신. 임포트는 사용자가 일으키는 행위다.

## 4. 개념 모델: 한계와 부하는 다른 것이다

두 종류를 섞으면 모든 규칙이 무너진다.

| | 한계 실측 | 부하 실측 |
|---|---|---|
| 답하는 질문 | 이 장비는 이 환경에서 얼마까지 되는가 | 지금 얼마가 흐르는가 |
| 들어가는 곳 | 성능층 근거(`performance_profile` 계열) | 수요(demand) 또는 자원별 부하 입력 |
| 수명 | 펌웨어와 기능 구성이 같으면 오래 유효 | 측정한 시점에만 유효 |
| 갱신 주기 | 드물다 | 자주 |
| 공유 가치 | 같은 모델을 쓰는 다른 설계에도 쓸모가 있다 | 이 설계에만 유효하다 |
| 틀렸을 때 | 장비를 과대·과소 평가한다 | 여력을 잘못 계산한다 |

수명과 공유 가치가 다르므로 **파일을 나눈다.** 한 파일에 담으면 `as_of`의 의미가 충돌한다. 한계는 반년 전 측정이어도 유효할 수 있지만 부하는 하루만 지나도 의심해야 한다.

- 한계 실측: `measured-limits.json`
- 부하 관측: `observed-load.json`

두 파일은 독립적으로 임포트된다. 하나만 있어도 쓸모가 있다.

## 5. 관측 최대값을 한계로 해석하는 규칙

이 문서에서 가장 중요한 절이다.

### 5.1 관측 최대는 한계의 하한이다

어떤 방화벽에서 관측된 최대 CPS가 36 Kcps라고 해서 그 장비의 한계가 36 Kcps인 것이 아니다. 부하가 거기까지 간 적이 없을 뿐일 수도 있다. 관측 최대는 **"적어도 이만큼은 된다"**는 하한이다.

이것을 한계로 등록하면 도구가 장비를 실제보다 약하게 본다. 그 결과는 헛된 증설 권고다. 상위 PRD의 "모르는 한계를 안전으로 바꾸지 않는다"는 원칙의 거울상이고, 방향만 반대인 같은 잘못이다. 확인되지 않은 것을 확인된 것처럼 쓰는 일이다.

### 5.2 관측값은 별도 종류로 저장한다

관측값은 `limit`이 아니라 `observedFloor`로 저장한다. **엔진은 `observedFloor`를 한계로 쓰지 않는다.** 사용률 계산에 들어가지 않는다.

한계로 승격할 수 있는 조건은 하나다. **포화가 확인된 관측이어야 한다.** 즉 그 값 이상의 요구가 실제로 있었고 장비가 넘지 못한 경우다. 드롭, 세션 거절, 큐 폐기, 오류율 증가 같은 포화 증거가 함께 기록되어야 한다.

| `saturated` | 저장 | 한계 승격 | `source.type` |
|---|---|---|---|
| `true` | `limit` + `observedFloor` | 가능 | `user_measured` |
| `false` | `observedFloor`만 | 불가 | 기존 근거 유지 |
| `unknown` | `observedFloor`만 | 불가 | 기존 근거 유지 |

기본값은 `unknown`이다. 파일이 포화를 단언하지 않으면 승격하지 않는다.

### 5.3 병기한다

`observedFloor`만 있는 축은 화면에서 한계와 나란히 보인다.

```
신규 세션   42 Kcps limit   (데이터시트 @ features off)
            36 Kcps 관측 하한 (2026-08, 포화 미확인)
```

이 표기는 두 가지를 동시에 말한다. 계산에 쓰는 한계는 데이터시트 값이고, 이 환경에서 실제로 본 것은 36 Kcps까지라는 것이다. 사용자가 판단할 재료를 주되 도구가 대신 결론 내리지 않는다.

### 5.4 모순 탐지

`observedFloor`의 가장 값진 쓰임은 승격이 아니라 **모순 검출**이다.

관측 하한이 현재 적용된 한계보다 크면 그 한계는 이 환경에 맞지 않는다. 장비가 데이터시트 값을 넘겼다는 뜻이고, 대개 조건 선택이 틀렸다는 신호다.

> `FW B · 신규 세션` 의 한계는 42 Kcps(데이터시트)인데 이 장비에서 58 Kcps 가 관측되었습니다. 적용한 근거의 측정 조건이 이 환경과 맞지 않습니다.

이 경우 해당 축을 `status: 'invalid'` 계열로 다루고 사용자에게 근거 재선택을 요구한다. 계산을 조용히 계속하지 않는다. 사용률 138%는 과부하가 아니라 잘못된 한계의 증상이다.

반대로 관측 하한이 한계보다 훨씬 낮은 것은 아무 정보가 아니다. 부하가 낮았을 뿐이다. 경고하지 않는다.

### 5.5 부하 관측의 집계 방식

부하 관측에도 같은 종류의 함정이 있다. 평균 부하로 여력을 계산하면 실제보다 여유 있게 보인다. 어떤 집계값인지 반드시 기록하고 화면에 표시한다.

집계 종류는 `max`, `p99`, `p95`, `mean`을 받는다. 기본 권고는 `p95`다. 순간 최대는 단일 표본 이상치에 흔들리고 평균은 피크를 지운다. 어느 것을 골랐는지가 결과의 의미를 바꾸므로 선택값을 결과 화면과 내보내기에 싣는다.

## 6. 데이터 형식

아래는 **제안**이다. 확정 전에 상위 PRD 7.2절의 `performance_profile` 스키마와 맞춰야 한다.

### 6.1 한계 실측

7.2절 스키마를 재사용하고 관측 메타데이터를 담는 `observation` 객체를 더한다. 7.2절이 요구하는 `conditions` 객체는 그대로 필수다. 조건 없는 값은 거부한다.

```yaml
# measured-limits.json 의 항목 하나 (개념 표기)
device_ref: { manufacturer, model }
axis: new_sessions_per_sec
value: 58000
unit: session_per_sec
scope: system
conditions:            # 7.2절 필수 객체. 실측이라고 면제되지 않는다
  features_enabled: [ips, logging]
  packet_size_bytes: null
  firmware_version: "7.4.3"
  test_method: production-observation
observation:           # 실측 전용 추가
  window_start: "2026-08-01T00:00:00Z"
  window_end: "2026-08-31T00:00:00Z"
  sample_interval_sec: 60
  sample_count: 44640
  aggregate: max
  saturated: true
  saturation_evidence: "session-table-full counter > 0"
source:
  type: user_measured
  retrieved_at: "2026-09-09"
  locator: "eks-zbx / host fw-b / item net.session.new"
```

`saturated: true`인데 `saturation_evidence`가 비어 있으면 `unknown`으로 강등한다. 포화를 주장하려면 근거를 적어야 한다.

### 6.2 부하 관측

```yaml
# observed-load.json (개념 표기)
as_of: "2026-09-09T03:00:00Z"
aggregate: p95
window: { start, end, sample_interval_sec, sample_count }
topology_fingerprint:        # 6.4절
  device_ids: [...]
  link_ids: [...]
entries:
  - target: { kind: link, from: spine-b, to: leaf-b }
    direction: forward
    axis: forwarding_bps
    value: 8600000000
  - target: { kind: device, id: fw-b }
    axis: new_sessions_per_sec
    value: 35600
```

부하 관측의 conditions와 scope는 선택 항목이다. 기록하면 현재 워크로드와 대조해 조건 일치 또는 불일치 집단으로 검증 리포트에 넣는다. 기록하지 않으면 임포트는 허용하되 조건 미기록 집단으로 분리한다. 이 규칙은 한계 실측의 조건 필수 규칙과 다르다. 부하 관측은 한계를 주장하지 않는다.

### 6.3 방향은 in/out으로 받지 않는다

모니터링 시스템은 보통 인터페이스 기준 in/out을 준다. in/out은 관측 지점에 종속이라 링크 방향으로 바로 번역되지 않는다. 같은 물리 링크의 한쪽 in이 다른 쪽 out이고, 관측 지점이 어느 장비인지에 따라 뒤집힌다.

그래서 파일이 `from`과 `to` 장비를 명시하게 요구한다. 엔진의 `directions.forward` / `directions.reverse`와 직접 대응시킨다. 모니터링 원본을 이 형태로 바꾸는 것은 사용자나 변환 스크립트의 몫이다.

제품이 모든 모니터링 벤더의 포맷을 추측하려 하면 틀린 방향으로 부하를 넣고 조용히 잘못된 답을 낸다. 변환 책임을 밖에 두는 대신 문서에 변환 예시를 제공한다.

### 6.4 토폴로지 지문

부하 스냅샷에 측정 시점의 자원 id 집합을 함께 담는다. 임포트할 때 현재 토폴로지와 비교해 차이가 있으면 경고한다.

반년 전 토폴로지로 계산한 "버틴다"는 계산은 정확하고 답은 틀리다. 이 실패는 화면에 아무 경고도 띄우지 않으므로 가장 위험하다. 지문 비교가 그 침묵을 깬다.

## 7. 기능 요구사항

### 7.1 파일 임포트

두 파일 종류를 각각 드래그 앤 드롭과 파일 선택으로 받는다. 기존 `readFile(input)`의 2MB 상한을 유지한다. 자원 700개 × 축 4개 규모에서도 항목 수가 3천 미만이라 충분할 것으로 **추정한다. 확인 필요.**

**인수 기준.** 잘못된 스키마의 파일을 넣으면 어느 항목의 어느 필드가 문제인지 위치와 함께 표시하고, 기존 프로젝트 상태를 바꾸지 않는다.

### 7.2 관측값의 한계 승격 게이트

5.2절의 표대로 동작한다. `saturated`가 `true`이고 `saturation_evidence`가 있을 때만 `user_measured` 한계로 등록한다. 그 밖에는 `observedFloor`로만 저장하고 계산에 넣지 않는다.

**인수 기준.** `saturated: false`인 항목을 임포트한 뒤 해당 축의 사용률과 한계가 임포트 이전과 같다. `observedFloor`는 화면에 표시된다.

### 7.3 모순 탐지

`observedFloor`가 적용된 한계보다 크면 해당 축을 정상 계산에서 빼고 근거 불일치로 표시한다.

**인수 기준.** 한계 42 Kcps에 관측 하한 58 Kcps를 넣으면 사용률 138%가 아니라 근거 불일치 판정이 나온다.

### 7.4 식별자 매칭

파일의 `target`을 토폴로지의 장비와 링크에 매핑한다. 자동 매칭은 id 일치를 먼저 시도하고, 실패하면 이름 정규화(대소문자, 구분자)로 시도한다. 장비에 모니터링 식별자를 적는 필드를 둘 것을 제안한다. 필드명은 미결이다.

미매칭 항목은 목록으로 보이고 수동 매핑을 받는다.

**인수 기준.** 20개 항목 중 8개가 미매칭일 때 `적용 12 / 미매칭 8`이 화면에 표시되고, 미매칭 목록을 열 수 있다.

### 7.5 부분 적용을 숨기지 않는다

일부만 매칭되어도 적용할 수 있다. 단 적용 범위가 항상 보인다. 매칭되지 않은 자원은 기존 근거를 유지하고, 그 자원의 출처 표시가 `user_measured`로 바뀌지 않는다.

**인수 기준.** 부분 적용 후 매칭되지 않은 자원의 `source.type`이 임포트 이전과 같고, `docs/display-layer-improvement-prd.md` 4절의 떨림 게이트에서 계속 흔들린다.

### 7.6 신선도 표시와 경고

`as_of`를 프로젝트에 기록하고 부하 스냅샷이 적용된 동안 화면에 표시한다. 임계 기간을 넘으면 경고한다. 임계값은 미결이다.

한계 실측은 `conditions.firmware_version`이 현재 설정과 다르면 경고한다. 펌웨어가 바뀌면 성능이 바뀐다.

**인수 기준.** 부하 스냅샷이 적용된 상태에서 `as_of`가 결과 화면과 내보내기에 모두 보인다.

### 7.7 토폴로지 지문 비교

6.4절의 비교를 임포트 시점과 재계산 시점 모두에서 수행한다. 자원이 추가·삭제되면 경고하고 어떤 자원이 달라졌는지 열거한다.

**인수 기준.** 부하 스냅샷을 적용한 뒤 장비 하나를 추가하면 지문 불일치 경고가 나타난다.

### 7.8 검증 리포트

상위 PRD 9절의 "실측 대조"를 만족하는 출력을 낸다. 부하 관측과 엔진이 계산한 부하를 축별로 비교한다.

- 축별 MAPE와 최대 오차
- 표본 수
- 조건이 일치하는 표본과 일치하지 않는 표본을 **별도 집단으로 분리**한다. 9절이 요구하는 사항이다
- 부호 있는 오차 분포. 계산이 체계적으로 크게 나오는지 작게 나오는지

**인수 기준.** 부하 스냅샷을 적용하면 검증 리포트를 열 수 있고, 축별 MAPE와 표본 수가 표시되며 조건 불일치 표본이 따로 집계된다.

### 7.9 익명 내보내기

실측 파일에는 내부 호스트명, 인터페이스명, 모니터링 항목 키가 들어 있다. 브라우저 밖으로 나가지 않지만 프로젝트 JSON과 SVG, PNG 내보내기에 실린다.

- `source.locator`는 기본적으로 이미지 내보내기에서 제외한다. 모니터링 경로까지 그림에 찍힐 이유가 없다.
- 장비 이름을 역할 기반으로 치환하는 `익명 내보내기` 선택지를 둔다. 기본값은 끔이다. 설계 리뷰에는 실명이 필요하다.

**인수 기준.** 익명 내보내기를 켜면 SVG에 원래 장비 이름 문자열이 존재하지 않는다.

## 8. 비기능 요구사항

| 항목 | 목표 |
|---|---|
| 외부 요청 | 없음. 파일 임포트만 |
| 파일 상한 | 2MB 유지. 초과 시 이유를 설명하고 분할을 안내 |
| 결정성 | 같은 파일을 같은 토폴로지에 적용하면 같은 결과 |
| 기존 상태 보호 | 임포트 실패가 기존 프로젝트를 훼손하지 않는다 |
| 되돌리기 | 임포트 적용이 `historyStep` 경로에 기록된다 |
| 개인정보 | 실측값과 모니터링 식별자는 로컬에 둔다. 이미지 내보내기에서 `locator` 제외 |

## 9. 검증 전략

**승격 게이트.** `saturated`가 `true`가 아닌 항목이 `limit`을 바꾸지 않는다. `saturation_evidence`가 빈 `true` 항목이 `unknown`으로 강등된다.

**계산 무영향.** `observedFloor`만 들어온 상태의 모든 사용률과 판정이 임포트 이전과 같다.

**모순 탐지.** 관측 하한이 한계를 넘는 항목에서 근거 불일치 판정이 나오고 사용률이 100%를 넘는 숫자로 표시되지 않는다.

**방향 매핑.** `from`과 `to`를 뒤집은 파일을 넣으면 `forward`와 `reverse` 부하가 서로 바뀐다. 방향 정보가 무시되지 않는다.

**부분 적용.** 미매칭 자원의 `source.type`과 떨림 진폭이 임포트 이전과 같다.

**지문 비교.** 자원 추가, 삭제, 이름 변경 각각에서 경고가 발생한다.

**스키마 거부.** conditions가 없는 한계 실측 항목을 거부한다. 부하 관측은 조건 미기록 집단으로 분리한다.

**검증 리포트.** 조건 일치 표본과 불일치 표본이 같은 집단으로 합산되지 않는다.

**익명화.** 익명 내보내기 결과에 원래 이름과 `locator` 문자열이 없다.

## 10. 결정 사항과 미결 사항

### 결정됨 (v0.1)

**한계 실측과 부하 관측을 다른 파일로 받는다.** 수명과 공유 가치가 다르고 `as_of`의 의미가 충돌한다.

**관측 최대는 한계가 아니다.** `observedFloor`로 저장하고 엔진이 한계로 쓰지 않는다. 포화가 근거와 함께 확인된 경우에만 승격한다.

**모순은 계산하지 않고 드러낸다.** 관측 하한이 한계를 넘으면 근거 불일치다. 사용률 138%로 표시하지 않는다.

**방향은 `from`/`to`로 받는다.** in/out을 해석하지 않는다. 변환 책임을 밖에 둔다.

**실측이라고 `conditions`를 면제하지 않는다.** 7.2절의 조건 필수 규칙을 그대로 적용한다.

**부분 적용을 허용하고 범위를 항상 표시한다.**

**토폴로지 지문을 함께 저장하고 비교한다.** 조용한 실패를 막는다.

**모니터링 제품 포맷을 해석하지 않는다.** 중간 형식을 정의하고 변환 예시만 제공한다.

### 미결

**부하 스냅샷의 신선도 임계.** 7일을 기본 경고 기준으로 적용한다. 경고는 화면과 보고서에 표시하며 계산값은 바꾸지 않는다. 사용자 설정으로 노출할지는 미결이다.

**모니터링 식별자 필드명.** 장비에 `metadata` 아래 둘지 별도 필드로 둘지, 이름을 무엇으로 할지.

**집계 기본값.** 파일은 `p95`, `p99`, `max`, `mean` 중 하나를 명시해야 한다. 값이 없으면 거부한다. 권고 기본값을 UI에 둘지는 미결이다.

**한계 실측의 공유.** 같은 모델의 실측값은 다른 설계에도 쓸모가 있다. 상위 PRD 7.3절이 정한 별도 데이터 저장소(`rack-mesh-devices`)에 기여하는 경로를 둘지, 로컬에만 둘지. 기여는 조건과 환경 정보 노출을 뜻하므로 신중해야 한다.

**포화 증거의 표준 목록.** `saturation_evidence`를 자유 문자열로 둘지 열거형으로 둘지. 열거형이면 축마다 다른 증거 종류가 필요하다.

**검증 리포트의 목표치.** 상위 PRD 14절이 MAPE 20% 이하를 잠정 목표로 적고 첫 표본 확보 후 조정하기로 했다. 이 임포트가 첫 표본을 만든다.

## 11. 작업 순서

1. 중간 형식 확정. 6절 스키마를 7.2절과 맞춘다. 이것이 정해지기 전에는 UI를 만들지 않는다.
2. 한계 실측 임포트와 승격 게이트. 5.2절과 5.4절. 모순 탐지를 같이 넣는다.
3. `observedFloor` 병기 표시.
4. 부하 관측 임포트. 식별자 매칭과 부분 적용.
5. 토폴로지 지문과 신선도 경고.
6. 검증 리포트.
7. 익명 내보내기.

## 12. 손대지 말 것

- `source.type` 열거값과 `SOURCE_TYPE_LABEL`. 새 종류를 추가하지 않는다. 실측은 이미 `user_measured`다.
- `evidenceApplicability`와 `acceptanceDigest`의 판정 로직. 임포트는 근거를 넣을 뿐 판정을 우회하지 않는다.
- 한계 실측의 conditions 필수 규칙. 부하 관측은 한계를 주장하지 않으므로 조건을 선택적으로 기록한다.
- `unknown`을 안전으로 바꾸지 않는 원칙. 이 문서는 그 원칙의 거울상을 추가할 뿐이다.
