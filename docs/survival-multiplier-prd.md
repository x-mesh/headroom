## 1. 한 줄 정의

장애가 없을 때의 여유 배수와 단일 장애 전수 스윕을 곱해, **어떤 장비 하나가 죽어도 현재 부하의 몇 배까지 받아내는가**를 하나의 숫자로 낸다.

## 2. 배경

엔진에는 필요한 조각이 이미 따로 있다. `growthLadder(activeResources, scale, warningThreshold)`가 배율 사다리를 계산해 결과 summary에 실리고, UI는 그것을 캔버스 부제의 `1.16배에서 초과` 문구로만 쓴다. 장애 스윕은 별도로 자원마다 `severs | overloads | absorbs` 판정을 내고 장애 주입 패널에 결과 문장으로 표시한다.

두 값은 각각 반쪽이다. `1.16배`는 모든 장비가 살아 있을 때만 참이고, `끄면 82%만 전달`은 현재 부하에서만 참이다. 실무에서 결정을 바꾸는 질문은 둘의 교차점에 있다.

> 정상시 1.16배까지 견딤. 최악 단일 장애 시 0.71배. 즉 현재 부하도 받아내지 못함.

`최소 headroom 14%`는 증설 회의에서 힘이 없다. "장비 한 대 죽으면 지금 부하도 못 버팁니다"는 결정을 바꾼다. 이중화, 용량, 다축 한계가 한 숫자에 들어간다.

이 계산은 정상 상태 결정적 엔진을 택한 결과로 가능해진다. 이산사건 시뮬레이터는 N-1 전수에 대해 배수 탐색을 다시 돌리는 것을 인터랙티브하게 할 수 없다. 5절의 계산 비용 논의가 이 이점의 한계도 함께 다룬다.

## 3. 목표와 비목표

### 목표

- 단일 장애 전수 중 가장 나쁜 경우의 여유 배수를 계산한다.
- 그 값이 1 미만이면 현재 부하조차 단일 장애를 견디지 못한다는 사실을 화면에서 단정한다.
- 어떤 장애가 최악인지, 그때 어느 자원의 어느 축이 막는지 함께 지목한다.
- 미확인 한계가 섞여 있으면 단일 숫자를 자신 있게 내놓지 않는다.

### 비목표

- 확률적 가용성. MTBF와 복구 시간을 입력받지 않고 99.9x% 같은 수치를 산출하지 않는다.
- 동시 다중 장애. N-2와 장애 도메인 단위 스윕은 `docs/domain-sweep-prd.md`가 다룬다.
- 전환 과정. VRRP 전환, BGP 수렴, 세션 동기화는 상위 PRD 3절 비목표다. 이 지표는 전환이 끝난 뒤의 정상 상태만 말한다.
- 증설 처방. "무엇으로 바꾸면 얼마가 되는가"는 `docs/device-substitution-prd.md`가 다룬다.

## 4. 지표 정의

### 4.1 이름

화면과 문서에서 **생존 배수**, 식별자는 `survivalMultiplier`를 쓴다. 계산값 이름 `headroom`은 상위 PRD 13절 결정대로 소문자를 유지하고, 생존 배수는 그것과 구별되는 별개 지표다.

### 4.2 정의

단일 장애 후보 집합 `C`에 대해

```
survivalMultiplier = min over f in C of multiplier(f)
worstFault         = argmin over f in C of multiplier(f)
```

`multiplier(f)`는 장애 `f`를 주입한 상태에서 `growthLadder`가 내는 배수, 즉 어떤 자원의 어느 축도 한계를 넘지 않는 최대 워크로드 배율이다.

### 4.3 최악의 기준은 배수다

최악을 전달률이 가장 낮아지는 장애로 정할 수도 있다. 그렇게 하지 않는다. 출력 지표가 배수이므로 선정 기준도 배수여야 한다. 두 기준이 다른 장애를 고르면 화면이 "최악은 A인데 A의 배수는 B보다 높다"고 말하게 된다.

### 4.4 단절은 배수 0이다

장애 `f`가 어떤 수요의 모든 경로를 끊으면 부하를 얼마로 줄여도 전달되지 않는다. 따라서 `multiplier(f) = 0`이다. 이 정의는 논리적으로 일관되고, 자동으로 단절이 최악으로 선정된다.

다만 `0`과 `0.71`은 성질이 다르다. `0.71`은 용량이 부족한 것이고 `0`은 경로가 없는 것이다. 증설로 고칠 수 있는 문제와 경로를 추가해야 하는 문제는 다르다. 그래서 숫자만 내놓지 않고 판정 라벨을 함께 낸다.

| 생존 배수 | 판정 | 뜻 |
|---|---|---|
| `0` | 단절 | 단일 장애로 경로가 끊긴다. 경로 추가가 필요하다 |
| `0 < m < 1` | 용량 부족 | 경로는 남지만 현재 부하도 못 받는다. 증설이 필요하다 |
| `1 <= m` | 견딤 | 현재 부하의 `m`배까지 받는다 |

### 4.5 후보 집합에서 끝점을 제외한다

수요의 출발지나 목적지 장비를 끄면 그 수요 자체가 사라진다. 이것은 인프라의 생존성이 아니라 서비스를 끄는 일이다. 스윕 결과에 이미 `endpoint` 불린이 있고 노드의 `SPOF` 배지도 끝점을 제외한다. 같은 기준을 쓴다.

제외했다는 사실은 숨기지 않는다. 지표 옆에 `끝점 2개 제외`를 표시한다. 상위 PRD의 원칙상 계산에서 빼고 말하지 않는 것은 허용되지 않는다.

### 4.6 미확인 축이 있으면 상한값이다

한계를 모르는 축이 경로에 있으면 그 축은 제약으로 작용하지 않는다. 따라서 계산된 배수는 실제 배수보다 크거나 같다. 즉 생존 배수는 **상한값**이다.

이 경우 단일 숫자를 단정하지 않는다. 표기는 `0.71배 이하`이고 미확인 축 개수를 함께 붙인다. 서비스 수용 기준에 대한 통과 판정은 기존 원칙대로 보류한다. `미확인 제약 4개 때문에 통과 판정은 보류됩니다`와 같은 문장 체계를 재사용한다.

모르는 값을 안전으로 바꾸지 않는다는 원칙이 여기서는 "모르면 더 좋아 보이게 만들지 않는다"로 나타난다.

## 5. 계산 계약과 비용

### 5.1 2단계 계산

1단계는 기존 장애 스윕이다. 자원마다 전달률과 등급(`severs | overloads | absorbs`)을 낸다. 이미 구현되어 있고 실시간으로 돈다.

2단계는 배수 탐색이다. 1단계에서 `severs`로 판정된 후보는 배수가 0으로 확정되므로 탐색하지 않는다. 남은 후보에 대해서만 `growthLadder`를 다시 돈다.

```
1단계: 후보마다 전달률 계산 (기존 스윕)
       severs 발견 시 multiplier = 0 으로 확정, 2단계 생략
2단계: severs 가 아닌 후보에 대해서만 배수 탐색
```

`severs`가 하나라도 있으면 생존 배수는 0으로 즉시 확정된다. 나쁜 설계일수록 계산이 싸진다.

### 5.2 규모 한계와 점진 계산

기본 시나오는 자원 20개(장비 10, 링크 10)라 즉시 끝난다. 2026-09-09 기준 환경의 200 장비 / 500 링크 / 1,000 수요 측정에서 단일 장애 스윕 700회는 약 3.2초, 생존 배수 698개 후보는 약 2.7초였다. 장비와 링크 합계가 20개를 넘으면 점진 계산으로 전환한다.

근사하지 않는다. 상위 후보 K개만 탐색해 대표값을 내놓는 방식은 "최악"이라는 단어를 거짓으로 만든다. 장애 후 최대 사용률이 높은 후보가 배수가 낮다는 관계는 축마다 부하 증가율이 달라 단조가 아니므로, 가지치기가 실제 최악을 놓칠 수 있다.

대신 점진 계산한다. 계산이 끝나지 않은 동안에는 숫자를 보이지 않고 진행 상태를 보인다.

- 장비와 링크 합계가 20개 이하면 동기 계산한다.
- 20개를 넘으면 단일 장애 스윕, 생존 배수, 도메인 스윕 순서로 유휴 시간에 전수 계산한다. 그동안 지표 자리에는 `계산 중 148/700`을 표시한다.
- 완료 전에는 부분 생존 배수를 표시하지 않는다. 부분 최솟값을 최종값처럼 읽히게 하지 않는다.
- 입력이 바뀌면 진행 중인 계산을 버리고 다시 시작한다. 부분 결과를 섞지 않는다.

### 5.3 결정성

같은 입력은 항상 같은 생존 배수와 같은 `worstFault`를 낸다. 배수가 동일한 후보가 둘 이상이면 자원 id의 사전순으로 정한다. 기존 스윕이 같은 방식의 동점 처리를 쓰고 있어 일관된다.

## 6. 기능 요구사항

### 6.1 지표 계산

정상시 배수와 생존 배수를 함께 계산하고, 생존 배수에는 `worstFault`(자원 id), 그때의 병목 자원과 축, 판정 라벨, 미확인 축 개수, 제외한 끝점 개수를 붙인다.

**인수 기준.** 기본 시나리오에서 생존 배수가 계산되고, 그 값이 장애 주입 패널에서 해당 자원을 실제로 끈 뒤 읽은 배수와 일치한다.

### 6.2 단절 우선 확정

후보 중 `severs`가 하나라도 있으면 생존 배수는 0이고 판정은 단절이다. 이때 2단계 탐색을 돌지 않는다.

**인수 기준.** `severs` 후보가 있는 시나리오에서 2단계 호출 횟수가 0이다.

### 6.3 끝점 제외와 그 고지

끝점 자원은 후보에서 제외하고, 제외 개수를 지표와 같은 자리에 표시한다.

**인수 기준.** 끝점 장비를 끄면 단절이 되는 시나리오에서 생존 배수가 0이 아니고, 화면에 제외 개수가 보인다.

### 6.4 미확인 축 표기

미확인 축이 하나라도 있으면 값에 `이하`를 붙이고 개수를 표시한다. 서비스 수용 기준에 대한 통과 판정은 보류한다.

**인수 기준.** 기본 시나리오는 미확인 축 4개를 가지므로 `이하` 표기와 `미확인 4개`가 함께 보인다.

### 6.5 서비스 수용 기준과의 결합

`topology.services`에 항목이 있으면 생존 배수만으로 판정하지 않는다. 서비스별로 최악 단일 장애에서의 전달률과 `requiredDeliveryRatio`를 비교해 통과 여부를 낸다.

서비스가 정의되어 있으면 **그 판정이 주 출력이고 생존 배수는 여유 정보**다. 서비스가 없으면 생존 배수가 주 출력이다. 기본 시나리오에는 `Public API` 서비스가 있으므로 현재는 전자다.

**인수 기준.** 최소 전달률 99%인 서비스를 정의하면, 최악 단일 장애에서 82%만 전달되는 경우 불통과로 판정되고 그 문장이 생존 배수보다 먼저 읽히는 자리에 놓인다.

## 7. 표시 요구사항

### 7.1 요약 타일

타일을 새로 늘리지 않는다. `docs/display-layer-improvement-prd.md` 6.4절이 추가하려는 여유 배수 타일 **하나에 두 값을 함께 넣는다.**

```
여유 배수
1.16×  정상
0.71×  최악 단일 장애 (FW A)
```

타일 개수가 늘지 않고, 두 숫자가 나란히 있을 때만 의미가 생기므로 같은 자리에 두는 것이 맞다. 타일 구성의 최종 결정은 `display-layer-improvement-prd.md` 6.4절이 소유하며 이 문서는 내용만 제안한다.

### 7.2 집계값이므로 떨지 않는다

생존 배수는 결론이지 관측이 아니다. `display-layer-improvement-prd.md` 4.1절 불변 조건 3에 따라 떨림 대상에서 제외한다. 타일이 `data-live-*` 속성을 갖지 않게 한다.

### 7.3 기준선 비교

`설계 변화` 패널에 생존 배수의 변화와 `worstFault` 변경을 추가한다. 병목 축 변경을 보고하는 기존 방식과 같은 형태를 쓴다.

```
생존 배수  +0.42   0.71× → 1.13×
최악 장애   CHANGED  fw-a → spine-b
```

### 7.4 내보내기

결과 JSON에 `survivalMultiplier`, `worstFault`, 판정 라벨, 미확인 축 개수, 제외한 끝점 목록, 계산 완료 여부를 담는다. 점진 계산이 끝나지 않은 상태로 내보내면 완료 여부를 `false`로 적는다. SVG와 PNG에도 지표와 판정 라벨을 적는다.

## 8. 비기능 요구사항

| 항목 | 목표 |
|---|---|
| 동기 계산 한계 | 자원 개수 임계값 이하에서 기존 재계산 예산 안에 들어온다. 임계값은 측정으로 고정 |
| 점진 계산 | 초과 시 1단계 등급을 먼저 내고 2단계를 이어서 돈다. 진행 상태를 표시한다 |
| 결정성 | 같은 입력은 같은 값과 같은 `worstFault`. 동점은 자원 id 사전순 |
| 근사 금지 | 후보 가지치기로 최악을 추정하지 않는다. 계산 전에는 숫자를 보이지 않는다 |
| 외부 요청 | 없음 |

## 9. 검증 전략

**정합성.** 계산된 `worstFault`를 실제로 주입한 뒤 읽은 배수가 생존 배수와 일치한다. 전수 시나리오에 대해 검증한다.

**단절 확정.** `severs` 후보가 있는 시나리오에서 생존 배수가 0이고 2단계 호출이 0회다.

**끝점 제외.** 끝점만 단절을 일으키는 시나리오에서 생존 배수가 0이 아니다.

**상한 방향.** 미확인 축을 한계값으로 채우면 생존 배수가 감소하거나 같고, 증가하지 않는다.

**단조성.** 어떤 자원의 한계를 올리면 생존 배수가 감소하지 않는다.

**결정성.** 같은 입력을 100회 계산해 값과 `worstFault`가 모두 같다.

**점진 계산 수렴.** 점진 계산의 중간 최솟값이 단조 비증가이고, 완료 시점의 값이 동기 계산 결과와 같다.

**떨림 제외.** 타일에 `data-live-*`가 없고 떨림 켬/끔에서 표시값이 같다.

## 10. 결정 사항과 미결 사항

### 결정됨 (v0.1)

**최악의 기준은 배수다.** 전달률이 아니다. 출력 지표와 선정 기준을 일치시킨다.

**단절은 배수 0이고 판정 라벨로 구별한다.** 경로 부재와 용량 부족은 처방이 다르므로 숫자만으로 말하지 않는다.

**끝점은 후보에서 제외하고 제외 사실을 표시한다.** 기존 `SPOF` 배지와 같은 기준이다.

**미확인 축이 있으면 상한으로 표기한다.** `이하`를 붙이고 개수를 보인다.

**근사하지 않는다.** 가지치기로 최악을 추정하는 대신 점진 계산하고 진행 상태를 보인다.

**타일을 늘리지 않는다.** 여유 배수 타일 하나에 정상시와 최악 장애시를 함께 넣는다.

**생존 배수는 자원 단일 장애 N-1만 대상으로 한다.** 도메인 N-1과 N-2는 별도 결과로 표시하고 생존 배수에 합치지 않는다.

### 미결

**동기 계산 임계값.** 자원 몇 개까지 동기로 돌릴지. 기준 브라우저와 하드웨어를 고정한 뒤 측정해 정한다. 상위 PRD 10절이 기준 환경을 Alpha 전에 고정하기로 했으므로 같은 시점에 정한다.

**배수 탐색의 재사용 가능성.** `growthLadder`가 매 후보마다 처음부터 도는지, 정상 상태 결과를 출발점으로 증분 계산할 수 있는지 확인 필요. 가능하면 2단계 비용이 크게 줄어든다.

**지표 이름의 사용자 검증.** `생존 배수`가 `여유 배수`와 나란히 놓였을 때 구별되는지. `N-1 배수`가 더 분명할 가능성이 있다.

**서비스가 여러 개일 때의 집계.** 서비스 각각의 통과 여부는 명확하지만 전체를 한 줄로 요약하는 규칙이 필요하다. 하나라도 불통과면 불통과로 보는 방식이 기본값으로 보이나 확인 필요.

## 11. 작업 순서

1. 2단계 계산 구조. 기존 스윕에 배수 탐색을 붙이고 `severs` 단축 경로를 넣는다.
2. 지표 계산과 결정성 테스트. 9절의 정합성, 단절 확정, 끝점 제외, 상한 방향.
3. 요약 타일 표시. `display-layer-improvement-prd.md` 6.4절 작업과 함께 진행한다.
4. 기준선 비교와 내보내기.
5. 규모 측정과 점진 계산. 임계값 고정.
6. 서비스 수용 기준 결합. 기본 시나리오에 서비스가 생긴 뒤에 의미가 있으므로 `docs/fault-sweep-surfacing-prd.md`와 기본 시나리오 작업 이후로 둔다.

## 12. 손대지 말 것

- 기존 장애 스윕의 등급 판정과 결과 문장. 이 문서는 그 위에 배수를 얹을 뿐이다.
- 끝점 제외 기준. `SPOF` 배지와 같은 기준을 유지한다.
- 미확인 축의 통과 판정 보류. 생존 배수도 같은 보류 규칙을 따른다.
