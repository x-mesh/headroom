# Headroom 첫 경험 사용성 테스트

처음 보는 사람이 제품의 목적과 장애 결과를 이해하고, 실제 구성도에서 원인을 찾아 복구할 수 있는지 관찰한다. 이 문서는 진행자용이다. 참가자에게 미리 보여주지 않는다.

## 준비

- 인프라 경험이 없는 참가자 1명과 인프라 설계·운영 경험이 있는 참가자 1명을 각각 진행한다. 두 명의 결과는 문제를 찾는 출발점이며 전체 사용자를 대표하지 않는다.
- 세션당 약 15분을 잡는다. 참가자에게 화면을 조작하면서 생각을 말해 달라고 요청한다. 진행자는 버튼 위치나 계산 의미를 먼저 설명하지 않는다.
- 기록에는 참가자 이름 대신 `비전문가 1`, `엔지니어 1`처럼 식별자를 사용한다. 녹화가 필요하다면 시작 전에 참가자에게 알리고 동의를 받는다.
- 첫 체험은 합성 예제다. 실제 인프라를 조작하거나 실측 데이터를 가져오는 과정은 포함하지 않는다.

### 검토 화면 실행

검토하려는 변경이 포함된 저장소를 실행한다. 공개 사이트나 다른 checkout은 검토 버전과 다를 수 있으므로, 테스트할 버전과 실행 위치를 먼저 확인한다.

1. Node.js가 설치된 환경에서 저장소 루트에 들어간다.
2. `npm start`를 실행한다.
3. 출력된 주소를 연다. 기본 주소는 `http://127.0.0.1:4173/`이다. 포트가 이미 사용 중이면 `RACK_MESH_PORT=4174 npm start`처럼 다른 포트를 지정하고 출력된 주소를 사용한다.
4. 참가자마다 새 브라우저 프로필 또는 새 시크릿 세션에서 `http://127.0.0.1:4173/?lang=ko`를 연다. 같은 시크릿 세션의 창을 재사용하면 이전 참가자의 작업 상태가 남을 수 있으므로 세션을 완전히 닫고 새로 시작한다. 주소의 포트는 서버 출력에 맞춘다.
5. 첫 화면에 **“장애가 나도 서비스는 버틸까요?”**가 보이는지 확인한다. 기존 브라우저 데이터를 지워서 초기화하지 않는다.

`127.0.0.1`은 서버를 실행한 컴퓨터에서만 열린다. 원격 참가자는 화면 공유와 원격 조작 등 참가자가 직접 조작할 수 있는 방법을 이용한다. 테스트가 끝나면 서버를 실행한 터미널에서 `Ctrl+C`를 누른다.

## 진행

### 1. 첫인상 — 약 1분

첫 화면을 열고 다음과 같이 말한다.

> 이 화면을 처음 본다고 생각하고 살펴봐 주세요. 무엇을 할 수 있는 도구로 보이나요? 생각나는 것을 말하면서 다음에 하고 싶은 행동을 해주세요.

처음 1분은 설명하지 않는다. 어느 버튼을 먼저 고르는지, 예상한 결과와 다른 점이 있는지 기록한다. 바로 자신의 설계를 시작하거나 예제를 둘러보는 것도 유효한 선택이다. 첫 행동을 평가한 뒤에는 필요하면 처음 화면을 새 시크릿 세션에서 다시 열어 다음 과제를 진행한다.

### 2. 장애 결과 이해 — 약 3분

> 예제에서 장애가 생기면 어떤 일이 일어나는지 확인해 주세요. 결과를 보고 무슨 일이 생겼고 왜 그런지 설명해 주세요.

참가자가 막히면 먼저 “지금 무엇을 확인하고 싶나요?”라고 묻는다. 그래도 진행하지 못하면 첫 화면에 있는 행동을 살펴보도록 한 번만 안내하고, 도움을 준 시점과 정확한 말을 기록한다.

관찰할 내용:

- 장애 실험을 시작했는가? 다른 선택을 했다면 무엇을 기대했는가?
- 결과에서 끊긴 대상과 공용 전원·두 SPINE의 관계를 스스로 설명했는가?
- `2개`, `12 Gbps`, `미확인 한계`를 무엇으로 이해했는가?
- 합성 예제라는 사실과 계산하지 않는 범위를 발견했는가?

### 3. 근거와 활용 — 약 3분

결과 화면을 보고 있는 동안 공통으로 묻는다.

> 이 결과만 보고 무엇을 알 수 있고, 무엇은 아직 확신할 수 없나요?

엔지니어에게는 이어서 묻는다.

> 실제 설계 검토에 쓰려면 어떤 입력이나 근거를 먼저 확인하겠습니까?

참가자의 표현을 그대로 기록한다. `미확인`을 안전으로 해석하는지, 합성 값과 실제 측정값을 구분하는지 특히 살펴본다. 설명을 제공했다면 그 이후 답변과 구분한다.

### 4. 구성도 확인과 복구 — 약 4분

> 방금 본 결과와 관련된 장비를 상세 구성도에서 찾고, 예제를 장애 이전 상태로 되돌려 주세요.

어떤 패널이나 버튼을 눌러야 하는지는 알려주지 않는다. 참가자가 결과 화면에서 바로 복구했다면 그 선택을 기록하고, 상세 구성도를 살펴볼 수 있는 방법을 찾을 수 있는지 별도로 물어본다.

관찰할 내용:

- 결과 화면에서 상세 분석으로 이동했는가?
- 실제 구성도에서 SPINE A와 SPINE B를 찾고 두 장비가 함께 중단된 이유를 연결했는가?
- 장애 항목 또는 기준 상태 복구 동작을 찾았는가? 복구 뒤 결과가 바뀐 것을 확인했는가?
- 모바일이라면 패널을 열고 닫는 과정에서 구성도나 다음 행동을 놓쳤는가?

### 5. 마무리 — 약 2분

> 가장 이해하기 어려웠던 순간은 언제였나요? 이 도구가 자신의 작업에 도움이 될 만한 상황이 있나요?

기능 요청과 실제로 막힌 행동을 따로 적는다. 바로 해결책을 제안하지 말고 참가자가 겪은 문제를 먼저 확인한다.

## 진행자 확인용 예제 결과

다음은 참가자에게 미리 알려줄 정답이 아니라 진행 중 결과가 정상적으로 열렸는지 확인하기 위한 값이다. 현재 합성 데모에서 PDU-3 공용 전원 장애를 주입하면 SPINE A와 SPINE B가 중단되고, 무경로 수요 2개와 미전달 부하 12 Gbps가 표시된다. 장애 결과 화면에는 미확인 한계 2개가 표시된다. 계산은 선언한 입력과 모델의 범위 안에서만 해석하며 패킷 동작이나 장애 복구 시간을 시뮬레이션하지 않는다.

값이 다르면 참가자에게 정답을 맞추도록 요구하지 말고, 열려 있는 버전·언어·시나리오·주입된 장애를 기록한 뒤 원인을 확인한다.

## 세션 기록

참가자마다 아래 블록을 복사해 사용한다. 완료 여부는 `도움 없이 완료`, `도움 후 완료`, `미완료` 중 하나로 적고, 시간을 재지 않았다면 비워 둔다.

```text
세션 식별자:
역할과 관련 경험:
일시 / 화면 크기 또는 기기:
브랜치와 실행 환경:

첫 1분에 설명한 제품 목적:
첫 행동과 예상한 결과:
장애 실험: 완료 여부 / 걸린 시간 / 도움:
결과와 원인에 대한 참가자의 설명:
합성 예제 및 미확인 한계 인지 여부와 근거:
상세 구성도에서 장비 찾기: 완료 여부 / 도움:
복구: 완료 여부 / 도움:
실제 활용에 필요한 입력·근거에 대한 답변:

막힌 지점: 화면 / 행동 / 참가자의 말 / 진행자 개입
예상과 달랐던 점:
참가자가 제안한 기능:
후속 확인이 필요한 질문:
```

## 결과 정리

두 세션을 마친 뒤 발견 사항마다 **관찰한 행동과 발화**, 발생한 참가자, 작업 완료 여부, 개입 여부를 적는다. 반복된 문제와 한 사람에게만 발생한 문제를 구분하고, 원인이나 해결책은 관찰 사실과 분리해 가설로 기록한다. 제품 변경은 그 가설을 바탕으로 우선순위를 정한다.
